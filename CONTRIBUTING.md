# Contributing to Packy

Thanks for considering a contribution. Packy is an early-stage project for packaging agent configuration and the Pi runtime into an installable artifact. Clear, focused changes are especially helpful while the project is still small.

## Before you start

1. Read the [README](./README.md) to understand the current scope and limitations.
2. Search existing [issues](https://github.com/KrishCodesw/Packy/issues) and pull requests before starting substantial work.
3. For a significant feature or architectural change, open an issue first to discuss the proposed approach.
4. Never include API keys, credentials, personal data, generated runtime archives, or other secrets in a commit.

## Development setup

Requirements: Node.js 22 or newer and npm.

\`\`\`bash
git clone https://github.com/KrishCodesw/Packy.git
cd Packy
npm ci
npm run dev
\`\`\`

Open http://localhost:3000 to use the builder.

## Making a change

- Keep pull requests focused on one problem or feature.
- Prefer small changes that are easy to review.
- Preserve the distinction between Packy and the upstream Pi runtime.
- Do not present unimplemented platforms or placeholder MCP configurations as functional.
- Never commit generated runtime caches, build output, or secrets.
- Update the README when user-facing behaviour, setup, limitations, or supported platforms change.
- Add or update tests for changed behaviour.

A suggested branch naming convention is \`feat/short-description\`, \`fix/short-description\`, or \`docs/short-description\`.

## Test before opening a pull request

Run:

\`\`\`bash
npm ci
npm test
npm run build
\`\`\`

The test suite currently covers the agent files generated by \`lib/harness.ts\`. The production build verifies that the Next.js application type-checks and builds. Runtime packaging and installation also need manual end-to-end testing when those paths change.

If a command fails, include the relevant error output in the pull request instead of reporting the check as passed.

## Pull requests

A good pull request includes:

- A clear explanation of the problem and the chosen solution.
- The behaviour that changed, including screenshots for UI changes when useful.
- Tests run and their results.
- Any platform, compatibility, security, or migration implications.
- Documentation updates when applicable.

Keep unrelated formatting or refactoring out of a focused bug fix. A maintainer may ask for changes or additional validation before merging.

## Reporting security issues

Please do not report exploitable vulnerabilities in public issues. Follow [SECURITY.md](./SECURITY.md) for private reporting guidance.
